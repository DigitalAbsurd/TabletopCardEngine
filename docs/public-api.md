# Public API

This is the reviewable inventory of what `OpenHoldemEngine.dll` exposes. Everything else in the
assembly (`Data/`, `Engine/`, `Mappers/`, `HoldemActionHandlers/`) is `internal`; the tests and the
demo reach it through `InternalsVisibleTo`, which package validation ignores.

## How the baseline is enforced

The library project sets `EnablePackageValidation` and points `PackageValidationBaselinePath` at
[`eng/api-baseline/OpenHoldemEngine.1.0.0-baseline.nupkg`](../eng/api-baseline/), a package built
from the tree and committed. The gate is the plain command, with no extra properties:

```
dotnet pack src/OpenHoldemEngine -c Release
```

It compares the freshly built assembly with the one inside the baseline package and fails with an
ApiCompat diagnostic on a break: `CP0001` for a removed type, `CP0002` for a removed member, and the
related `CP` rules for changed signatures, visibility or base types. `dotnet build` does not run
package validation; only `pack` does, which is why it is one of the gates.

What it does not catch: ApiCompat compares the binary surface, so a change that only breaks source
compatibility, such as removing a parameter's default value, passes. Review that by hand, against the
signatures below.

The baseline is a committed file rather than a published version because there is no published
version yet. Once 1.0.0 is on nuget.org, the project switches to `PackageValidationBaselineVersion`.

## How to change the baseline

A change to the public surface and the new baseline go in **the same pull request**:

1. Make the API change.
2. Re-pack the baseline from the changed tree:

   ```
   dotnet pack src/OpenHoldemEngine -c Release -p:Version=1.0.0-baseline -o eng/api-baseline
   ```

3. Regenerate the inventory below (step 2 has already built the assembly it reads):

   ```
   pwsh ./scripts/list-public-api.ps1 -Update
   ```

4. Run `dotnet pack src/OpenHoldemEngine -c Release` again; it must be green.
5. Say in the pull request which members were removed or changed, and why a break is acceptable.

Never suppress the diagnostics instead: no `CompatibilitySuppressions.xml`, and no
`ApiCompatGenerateSuppressionFile`. A suppressed break is a baseline that no longer means anything.

Every baseline in `eng/api-baseline/` holds one `lib/net10.0` asset, because the packages target
`net10.0` only. Package validation compares assets per target framework, so moving the packages to
another framework makes `dotnet pack` fail with `PKV006` ("Target framework net10.0 is no longer
supported in the latest version") before it compares a single member. That is the one case where
every baseline is re-packed without a surface change: first confirm the members did not move (no
`CP00xx` diagnostic, and step 3 regenerates the inventory below with no diff), then re-pack each
package with `-p:EnablePackageValidation=false`, since validating against the old-framework
baseline is exactly what fails, and run the plain gate again.

## The provider packages

`OpenHoldemEngine.Sqlite` and `OpenHoldemEngine.PostgreSql` each have their own baseline,
[`eng/api-baseline/OpenHoldemEngine.Sqlite.1.0.0-baseline.nupkg`](../eng/api-baseline/) and
[`eng/api-baseline/OpenHoldemEngine.PostgreSql.1.0.0-baseline.nupkg`](../eng/api-baseline/),
enforced the same way by `dotnet pack src/OpenHoldemEngine.Sqlite -c Release` and
`dotnet pack src/OpenHoldemEngine.PostgreSql -c Release`. Each provider's public surface is one
class with two `UseHoldem*` overloads and its migrations are `internal`. The baselines are packed without validation, because there is nothing to compare the first one with:

```
dotnet pack src/OpenHoldemEngine.Sqlite -c Release -p:Version=1.0.0-baseline -p:EnablePackageValidation=false -o eng/api-baseline
dotnet pack src/OpenHoldemEngine.PostgreSql -c Release -p:Version=1.0.0-baseline -p:EnablePackageValidation=false -o eng/api-baseline
```

The inventory below covers the core package only.
